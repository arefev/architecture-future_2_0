# План управления рисками

## Архитектурные риски

### Несовместимость доменных моделей

**Меры:**

* Введение **Domain Governance Board**
* Использование **data contracts**
* Назначение **Domain Data Owner** в каждом домене

**Тип решения:**
Управленческое + архитектурное

### Миграция данных из Legacy DWH

**Меры:**

* Мост совместимости Camel → Kafka (постепенная миграция)
* Incremental data mirroring
* Дублирование проверок качества данных (DQ)

**Тип:**
Техническое

### Ошибки при переходе на event-driven

**Меры:**

* Schema Registry
* Соглашения по событиям (naming, versioning)
* Dead-letter queues (DLQ)

**Тип:**
Техническое

## Технологические риски

### Производительность ClickHouse

**Меры:**

* Шардирование
* Использование материализованных представлений
* Отдельные кластеры под горячие и холодные данные

---

### Нехватка GPU для ИИ

**Меры:**

* Автоскейлинг GPU нод
* Кэширование моделей
* Периодическое обучение, не real-time

---

### Неопытность команды в Kafka

**Меры:**

* Обучение персонала
* Создание platform-team
* Введение SLA на события

---

## Организационные риски

### 7) Сложности с границами доменов

**Меры:**

* Митапы доменных команд
* Event Storming сессии
* Обновление архитектурных артефактов каждые 2 недели

---

### Сопротивление изменениям

**Меры:**

* Пилоты в одном домене
* Демонстрация быстрых побед
* Обучение сотрудников работе с BI

---

### Недостаток компетенций

**Меры:**

* Менторство
* Курсы по Terraform, Kubernetes, Data Engineering
* Внедрение внутренних best practices
